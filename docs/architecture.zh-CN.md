# RelayScope 架构

[English](architecture.md) | **中文**

## 系统形态

RelayScope 是一个模块化单体。正常生产运行时是一个 Go 二进制，同时服务公开应用、管理后台、JSON API、调度器、采集器和维护任务。SQLite 是唯一的数据库。

未经实测需求和架构决策记录批准，不允许引入 Redis、消息队列、独立时序数据库或独立前端应用服务器。

```text
浏览器 / API 客户端
        |
Go HTTP 服务
  |-- 公开查询与静态资源
  |-- 管理员 API
  |-- 调度器与有边界的 worker 池
  |-- 适配器注册表
  |-- 模型匹配器
  |-- 会话与人机验证协调器
        |
SQLite (WAL)
        |
可选的短生命周期浏览器 / FlareSolverr 进程
```

## 包边界

计划中的内部包：

- `internal/config`：经过校验的应用配置。
- `internal/store`：SQLite 模式（schema）、迁移、事务与查询方法。
- `internal/domain`：稳定的领域类型与状态语义。
- `internal/matcher`：确定性的模型规范化、分词、匹配与预览。
- `internal/adapter`：适配器接口、注册表、配置 schema 与实现。
- `internal/collector`：采集编排、重试、完整性检查与事务性写入。
- `internal/scheduler`：带抖动的逐站点调度，同一站点不重叠运行。
- `internal/session`：加密的站点会话与 OAuth 登录恢复协调。
- `internal/challenge`：人机验证挑战检测与可替换的 FlareSolverr/浏览器恢复。
- `internal/httpserver`：公开与管理员处理器。
- `web`：嵌入的静态前端源码与构建产物。

管理端的站点删除是软删除：历史数据在保留期内继续留存以备恢复，被删除的站点会被停用并排除在活跃查询和调度之外。恢复是显式操作，会把站点还原为禁用状态，避免恢复时意外触发一次采集。

适配器是架构意义上的「编译期插件」，不是 Go 运行时的 `plugin` 包。每个适配器都是独立注册的模块，带有元数据、配置 schema、发现逻辑与采集逻辑。这样既避免了不安全的动态加载，又让各接入保持可独立测试、可独立启用、易维护。

## 适配器契约

适配器接收不可变的站点定义和一个受限的抓取客户端。它绝不能直接写数据库。

它返回：

- 来源身份与观测到的来源时间；
- 模型目录是否完整；
- 发现的原始模型；
- 每个模型的原始站点分组；
- 可用时的当前聚合指标；
- 来源提供的时间桶；
- 类型化的采集诊断；
- 少量适配器特有的扩展数据。

抓取客户端提供 HTTP、已认证 HTTP、已过验证 HTTP 和浏览器上下文四种抓取模式。适配器只申请某种能力，自己不启动浏览器。

## 采集流程

1. 只有当站点没有进行中的运行时，调度器才创建新的运行。
2. 适配器在数据库事务之外抓取目录或批量接口。
3. 匹配器从完整目录中选出相关的原始模型。
4. 若批量接口不可用，适配器只为选中的模型获取详情数据。
5. 采集器在内存中校验并规范化结果。
6. 存储层写入有边界的批量事务并推进公开数据版本号。
7. 前端条件轮询感知到新版本号。

HTTP 并发默认全局三个站点。单个站点内部串行执行，除非适配器声明安全并发上限为二。浏览器与 FlareSolverr 操作全局串行。

## 增量历史

适配器会重新抓取一段有边界的重叠窗口，通常就是来源公开的 24 小时窗口，并返回其中所有真实来源时间桶，保持其稳定的边界与分辨率。时间桶的唯一键由来源分组身份、指标窗口开始时间和来源时间桶分辨率组成。重复观测覆盖同一行，因此后续运行可以修复此前失败或错过时点的采集留下的缺口，而不会伪造样本。数据库保留 72 小时，使重叠修复与留存策略解耦。

优先使用嵌入在目录或批量响应里的历史数据，因为它不产生逐模型的网络扇出。只暴露当前值或目录存在性的来源无法参与历史修复；其适配器绝不能合成时间桶。零样本的不完整当前桶会为溯源而保留，但不会取代最新有采样的当前状态。

对于无法避免的逐模型详情请求，即使部分请求失败也提交成功的模型。有边界的类型化诊断会把这次运行标记为部分完成。若所有详情请求都失败，采集在写库前即失败，最近一次成功快照继续生效。

当前快照与历史时间桶分开存储，公开列表查询因此保持轻量。网络操作绝不持有 SQLite 事务。

历史时间桶与冗长的运行诊断三天后过期。身份、配置、当前快照、模型移除证据和精简的运维摘要继续保留。

## 浏览器进程

主二进制绝不会为了调度而让 Chromium 常驻运行。浏览器操作是一种例外的外部能力：

- OAuth 工作流：导入用户本地浏览器中建立的最小会话包，并以认证加密存储。
- Cloudflare 工作流：用固定版本的 FlareSolverr 解决偶发的托管或勾选框式验证，然后复用放行凭据或在已通过验证的上下文内抓取。

Cloudflare 浏览器操作需获取一个全局租约，带有硬超时、内存感知的启动参数、冷却期和进程清理。生产目标是升级后的服务器；由于浏览器内存占用是突发式的，仍建议配置 swap。

## 前端交付

公开界面与管理后台是嵌入 Go 二进制的静态资源。实现上应使用浏览器原生 JavaScript，或仅在确实显著降低复杂度时使用构建期轻量框架。禁止运行时 Node.js。

公开更新采用感知版本号的条件轮询，间隔 30 到 60 秒。对一个大约每 20 分钟更新一次的数据源来说，WebSocket 和服务器推送事件并无必要。

## 安全

- 管理员认证使用强随机生成的密码、自适应密码哈希、安全 Cookie 会话、CSRF 防护与登录限速。浏览器会话同步使用短时效、绑定源（origin）的配对令牌；扩展永远不会拿到管理员密码。
- 站点凭据与 Cookie 使用认证加密，密钥来自数据库之外。
- 日志对 Cookie、授权头、API Key 以及已知含凭据的查询参数做脱敏。
- FlareSolverr 只绑定环回地址，绝不对外暴露。
- 浏览器自动化仅限于已登记站点与 OAuth 提供方的域名白名单。
- `.env` 文件、数据库文件、浏览器配置目录、Cookie 和密钥绝不进入 Git。

## 容量目标

对几十个站点、三天的数据跨度而言，SQLite 足够。上线前必须用有代表性的生成数据对 schema 和索引进行实测。维护任务以小批量删除过期行并做增量页回收；它不会频繁执行全库 vacuum。
