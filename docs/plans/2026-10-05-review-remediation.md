# 审查问题有序修复计划

> 使用子代理在当前会话实施，按需求符合性、代码质量两阶段复核。

目标：修复 2026-10-05 审查中除状态小字对比度与重复染色方案外的全部事项；公告修改不得导致重复推送或历史重放。

架构：保留模块化单体与静态前端。以已有路由观测分支为基线，在独立修复分支整合；后端在存储事务与事件去重边界修复，前端收敛请求状态与订阅逻辑，布局统一遵循内容可用宽度。

技术：Go（后端语言）、SQLite（嵌入式数据库）、原生 JavaScript（前端脚本）、CSS（样式表）。

## 任务与验证

1. 后端登录与额度：internal/linuxdo/oauth.go（登录服务）、internal/httpserver/routes.go（路由）、internal/httpserver/user_routes.go（用户操作）、internal/store/wish_credits.go（额度存储）。先补浏览器绑定、请求取消与事务回滚回归测试，再实现绑定登录随机值和原子免费助力。会员退款按用户确认的规则实施，保留其他权益。运行相关包测试。
2. 公告事件：internal/store/announcements.go（公告）、internal/store/notifications.go（待发队列）、迁移与通知调度。先测试相同内容重复采集、标题修改、原文修改、迁移后的旧消息、重试与历史回填，再引入稳定内容版本去重。已有待发记录不能导致同版重复新建；升级不能重放历史。运行存储与通知测试。
3. 前端可靠性：web/public/dashboard.js（看板）及可直接测试的功能模块。补同版本失败重试、快速切换详情、关闭后返回、取消订阅失败、单站时间筛选测试。统一请求错误与异步提交边界，提取轮询状态、偏好同步、订阅管理中实际可独立测试的职责。
4. 界面：公开页结构、看板与外壳样式、后台基础样式。恢复手机导航/通知，按内容宽度重排工具栏，收起手机筛选、增加局部搜索、统一控件尺度与焦点、稳定抽屉动效、拆分公告与详情入口。明确保留状态颜色、卡片底色、粗左边框、状态徽标字号，不实施报告第 117 行方案。通过模拟服务验证 390/中宽/1440 宽度与深浅主题。
5. 工程：复用持续集成检查并使发布依赖同一提交检查；限定发布提交来源；排除本地凭据文档与各类环境文件。格式化已有不规范文件。运行后端测试、静态检查、前端测试、构建、格式检查与配置验证。
6. 收尾：交叉复核需求覆盖与代码质量，补关键决定记录和实施结果；复核没有凭据进入变更。保留原审查、截图与缓存，不删除文件，不自动推送或发布。

## 边界

- 禁止删除文件；既有分支保留。
- 公告的网络发送无法单靠本地队列承诺外部平台的严格恰好一次；发送成功后落库失败的处理必须明确，不能把普通重复采集变成重复推送。
- 不在真实用户账户上发送测试通知或发起支付。
- 缺失的产品决策单独确认，不阻塞独立任务。
