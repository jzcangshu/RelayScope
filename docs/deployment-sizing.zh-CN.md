# 部署容量指南

[English](deployment-sizing.md) | **中文**

本文描述经过实测的资源包络以及各部署档位背后的假设。它是一份选型指南，不承诺任意适配器或人机验证负载都符合同样的包络。

## 实测生产基线

参考部署于 2026-08-24 在 Debian 13 上运行发布版服务并完成测量：

| 项目 | 实测值 |
| --- | ---: |
| 站点数 / 启用 / 需要会话 | 36 / 31 / 10 |
| 采集器 HTTP 并发 | 3 |
| 采集间隔 | 15 分钟 |
| 最近 24 小时采集次数 | 2,586 |
| 最近 24 小时写入的指标时间桶 | 79,392 |
| SQLite 文件 | 90.5 MB |
| 原始模型 / 站点分组 | 2,122 / 1,698 |
| 采样期间 RelayScope RSS | 42-53 MB |
| RelayScope 观测到的 cgroup 峰值 | 58.6 MB |
| 60 秒空闲/正常采样期间 RelayScope CPU | 单核的 1.7-1.9% |
| 公开健康端点延迟 | 本地 0.3-0.7 ms |
| 采样期间 FlareSolverr RSS | 106 MB |
| FlareSolverr 观测到的 cgroup 峰值 | 1.07 GB |

生产主机为 8 vCPU、8 GB 内存、2 GB swap、40 GB 磁盘。服务自身刻意限制为三个并发站点 HTTP 操作和四个 SQLite 连接；测量期间主机仍有大量富余容量。

## 推荐档位

### 仅 RelayScope

适用于不带 FlareSolverr 或 Chromium 的公开采集：

- **最低：** 1 vCPU、512 MB 内存、2 GB 可用磁盘、1 GB swap。
- **推荐：** 1-2 vCPU、1 GB 内存、10 GB 可用磁盘、1-2 GB swap。
- **宽裕：** 2 vCPU、2 GB 内存、20 GB 可用磁盘，适合更大的目录、备份和日志。

512 MB 的最低档假设约 40 个站点、默认并发、常规 JSON 载荷，且主机上没有其他吃内存的服务。它是运维下限，不是留有余量的目标值。

### RelayScope + FlareSolverr

把 FlareSolverr 及其浏览器进程视为独立负载：

- **最低：** 2 vCPU、2 GB 内存、4 GB swap、10 GB 可用磁盘。
- **推荐：** 2-4 vCPU、4 GB 内存、20 GB 可用磁盘。

不要在 768 MB 主机上运行 Chromium/FlareSolverr。实测 FlareSolverr 峰值超过 1 GB，尽管其稳态 RSS 只有约 106 MB。保留现有的 1 GB `MemoryHigh` 和 1.5 GB `MemoryMax` 限制，并监控 OOM kill。

## 容量模型

设间隔为 `I` 分钟、启用站点数为 `N`，标称采集速率为

`collections/day = N * 1440 / I`。

按 15 分钟间隔，40 个站点每天最多产生 3,840 次采集。参考部署实际为 2,586 次/天，因为停用、失败和延迟的站点并不会每次标称运行都完成。

调度器每轮最多选取 100 个到期站点。因此文档化的运行目标是默认间隔下**大约 40-60 个站点**。在启用/到期站点超过 100 个之前，先在实际适配器上测量采集时长与积压；提高 HTTP 并发会同时增加网络压力和内存占用。

SQLite 存储受 72 小时历史清理约束，但删除行后文件不会自动收缩。需要为当前文件、WAL/checkpoint 开销和备份预留空间。实用的预算公式：

`磁盘预算 = 10 * 当前数据库大小 + 2 * 最大备份 + 2 GB 日志/系统`

对实测的 90.5 MB 数据库来说，这仍远低于 5 GB。建议以 10 GB 可用磁盘为下限，让增长、升级和恢复副本不至于演变成故障风险。

## 扩容信号

以下任一情况持续 15 分钟时，应增加资源或降低站点负载：

- `running` 状态的采集运行持续逼近调度器的 3 分钟超时；
- 到期站点在多个调度周期被反复推迟；
- RSS 超过主机内存限制的 70%；
- SQLite WAL 或数据库写入持续出现 `database is locked` 阻塞；
- FlareSolverr 触及 `MemoryHigh` 或被 OOM 管理器杀死。

第一个扩容动作应是降低站点频率或隔离 FlareSolverr。只有在对远端站点限速和 CPU/内存余量完成测量之后，才提高采集器并发。
